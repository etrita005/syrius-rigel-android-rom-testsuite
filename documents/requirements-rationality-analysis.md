# Android 系统软件需求合理性分析

## 1. 文档目的

本文对 `documents/安卓系统软件需求.md` 中面向 Android 13（API 33）的系统软件需求进行合理性审查，目标是识别以下问题：

- 重复、空白或已经被替代的需求；
- 违反 Android 13 安全模型、隐私原则或兼容性要求的需求；
- 使用了废弃接口、过时概念或错误技术语义的需求；
- 缺少明确对象、状态模型和验收条件的需求；
- 与当前机器人上位机的硬件配置或产品定位不匹配的需求；
- 虽然可以通过定制 ROM 实现，但投入、维护风险或安全代价明显高于业务价值的需求。

本文仅提供需求审查和调整建议，不修改原始需求基线，也不代表具体功能已经实施或取消。

## 2. 总体结论

当前需求清单不适合直接作为开发和交付验收基线。清单同时混合了以下四类内容：

1. 机器人上位机真正需要的设备管控能力；
2. 普通消费手机的系统功能；
3. 不同手机厂商私有 MDM API 的能力对照；
4. ROM、Framework、系统应用、MDM、bootloader、recovery、服务端后台等不同层级的建设任务。

定制硬件和 ROM 可以突破公开 Android SDK 的限制，因此“公开 API 不支持”本身并不等于需求不合理。但是，ROM 可修改也不意味着以下设计是合理的：

- 建立可以绕过设备安全边界的后门；
- 破坏 Android 必需的隐私、安全和资源使用提示；
- 承诺硬件、运营商或第三方应用无法保证的数据；
- 用绝对化语言要求所有异常场景静默；
- 用一个接口名称覆盖多个完全不同的系统对象；
- 为当前硬件不存在的能力制定必选验收指标。

建议将需求重新整理为机器人核心必选、硬件条件适用、消费手机可选和拒绝实现四个级别，再进入开发排期。

## 4. 不应按当前形式实现的需求

### 4.1 ASR-0038：授予应用系统权限

“系统权限”不是一种统一的权限类型，其中可能包括 signature 权限、privileged 权限、角色权限、AppOps、受保护系统设置和 Binder 服务权限。将其设计成按权限名称任意授权的通用接口，会形成严重的提权通道。

建议：

- ROM 构建时使用明确的 `privapp-permissions` 白名单；
- 运行时接口只接受预定义权限枚举；
- 同时校验目标包名、签名证书和调用方身份；
- 禁止业务应用动态获取设备擦除、软件安装、系统设置写入等控制面权限；
- 记录授权、撤销、调用者和失败原因审计日志。

### 4.2 ASR-0041：免交互授予外部存储路径访问权限

Android 13 的分区存储、Storage Access Framework、媒体权限和应用专属目录具有不同的授权模型，不能将任意文件路径统一转换为一个稳定的运行时权限。

建议先区分：

- 应用专属目录；
- 公共媒体文件；
- SAF 文档树；
- 外接 USB/SD 存储卷；
- 受 ROM 控制的机器人共享数据目录。

机器人业务如确实需要跨应用共享文件，优先建设受签名权限保护的专用 ContentProvider 或文件服务，而不是开放任意路径。

### 4.3 ASR-0060、ASR-0061：隐藏前台服务和常驻通知

前台服务通知是 Android 用来提示资源消耗和敏感后台行为的系统机制。强行删除此类通知可能破坏前台服务生命周期、系统兼容性和故障可观测性。

建议：

- 非必要任务不使用前台服务；
- 必须使用时采用低重要性、无声音的通知渠道；
- 机器人 kiosk 模式可以隐藏状态栏界面，但不应删除通知框架中的前台服务记录；
- 系统故障、OTA、过热和存储耗尽通知必须保留。

官方依据：[Android Services overview](https://developer.android.com/develop/background-work/services)。

### 4.4 ASR-0083、ASR-0085：设置或删除 Device Owner、Profile Owner

Device Owner 是设备管理信任根，标准 Android 要求在未完成配置的设备上通过 provisioning 建立，不能作为普通运行时开关供业务应用任意变更。

建议改为：

- 工厂初始化或首次开机流程设置 Device Owner；
- MDM 只提供所有者状态查询和健康检查；
- 删除所有者应进入受控维修或恢复出厂流程；
- 不向普通业务应用暴露任意设置、删除 Owner 的命令。

官方依据：[DevicePolicyManager](https://developer.android.com/reference/android/app/admin/DevicePolicyManager.html)。

### 4.5 ASR-0101：查询浏览器访问记录

查询任意浏览器的访问历史违反应用沙箱，且不同浏览器的数据结构、隐私策略和无痕模式不同，无法形成通用兼容接口。

只有在预装并由项目维护的专用浏览器主动提供审计接口时才合理。接口还应规定数据保留周期、脱敏、访问授权和无痕模式处理规则。

### 4.6 ASR-0125：应用数据备份和恢复

不能承诺透明备份、恢复所有第三方应用。应用可以关闭备份或排除文件；缓存、`noBackupFilesDir`、设备相关标识以及部分凭据不能直接恢复；数据库还需要一致性处理。

建议改为“支持已适配业务应用的数据导出和导入协议”，由业务应用定义版本兼容、数据校验、密钥迁移和失败回滚流程。

官方依据：[Back up user data with Auto Backup](https://developer.android.com/identity/data/autobackup)。

### 4.7 ASR-0135、ASR-0136：通过本地 VPN 实现域名和 IP 黑白名单

需求目标本身合理，但当前方案不能被描述为无条件的全局安全边界：

- Android 同一用户通常只能有一个活动 VPN，本地防火墙会与业务 VPN、始终在线 VPN 冲突；
- 加密 DNS、直接 IP、CDN、QUIC、IPv6 和应用自带网络栈会降低域名归因准确性；
- 域名对应的 IP 会动态变化，同一个 IP 也可能承载多个域名；
- VPN 服务退出、崩溃或未启动时需要明确 fail-open 或 fail-closed 行为。

建议把验收边界写清楚，并评估在 ROM 网络栈或 eBPF/netd 层实现设备级防火墙。

### 4.8 ASR-0291～ASR-0298：VoIP 通话自动录音和转发

将所有第三方 VoIP 应用作为通用录音目标不合理。Android 对 `VOICE_COMMUNICATION` 等音频用途施加隐私捕获限制，不同 VoIP 应用还可能使用不同音频路径、硬件加速和防捕获策略。

建议：

- 只支持自研或明确适配的 VoIP 应用；
- 由通话应用主动输出录音流；
- 明示录音状态；
- 规定加密、留存、删除、访问审计和地区法律合规；
- 不建设可静默监听所有第三方通话的 ROM 后门；
- “录音转发”必须经过单独的安全和隐私评审。

官方依据：[AudioAttributes capture policy](https://developer.android.com/reference/android/media/AudioAttributes)。

### 4.9 ASR-0368：执行 Unlock Screen

允许 MDM 绕过凭据直接解锁，会破坏锁屏、文件加密和硬件密钥的安全边界，不应实现。

机器人设备如不需要传统人工锁屏，应采用以下设计：

- kiosk/LockTask 模式；
- 开机后自动进入业务应用；
- 受控维修模式；
- 物理在场加管理员认证；
- 必要时通过受控 wipe 恢复，而不是绕过锁屏认证。

### 4.10 ASR-0378：禁用 Hard Reset

完全取消物理恢复通道会增加设备永久锁死和现场不可维修的风险。普通用户入口可以禁用，但必须保留经过物理在场验证、授权工厂工具或签名维修包控制的恢复路径。

该能力也不只是 ROM/MDM 功能，还涉及 bootloader、recovery、按键组合和防回滚策略。

### 4.11 ASR-0435：不弹任何系统弹窗

这是无法安全验收的绝对化要求。过热、低电量、系统崩溃、权限失败、存储耗尽、升级失败和硬件异常不能全部静默吞掉。

建议重写为：

> 在正常机器人业务流程中不得出现需要人工处理的非致命系统弹窗；致命故障、安全事件及不可恢复错误应进入统一故障页，并同步写入设备日志和远程告警系统。

### 4.12 ASR-0443：禁止所有系统升级入口，包括 recovery

永久禁止全部升级和恢复入口会阻止安全补丁、现场救援和故障恢复。合理目标应是禁止普通用户和未授权应用发起升级，同时保留签名 OTA、授权工厂工具和物理维修模式。

还应定义：

- 禁用策略的最长有效期；
- 紧急安全更新是否可以覆盖禁用策略；
- MDM 离线或损坏时如何恢复；
- recovery 和 bootloader 的授权验证方式；
- 升级失败后的 A/B 自动回滚路径。

### 4.13 ASR-0462：默认禁用所有应用通知

无条件禁用全部通知会同时隐藏前台服务、OTA、过热、低存储、网络故障和系统安全提示，与设备可靠性目标冲突。

建议改成：

> 默认禁止普通第三方应用通知，保留机器人业务、MDM、OTA、系统故障、温度、电池、存储和安全事件通知白名单。

## 5. Android 13 技术语义错误或已经过时的需求

### 5.1 ASR-0205：禁止模拟定位

当前备注通过写入 `Settings.Secure.mock_location` 实现禁止模拟定位。该设置对应的 `ALLOW_MOCK_LOCATION` 从 API 23 起已经废弃，不能作为 Android 13 的可靠控制和验收依据。

建议控制开发者选项入口、允许的 mock-location 应用及对应 AppOp，并分别验证普通应用、平台应用和 adb 场景。

### 5.2 ASR-0314：设置定位模式

`Settings.Secure.LOCATION_MODE` 从 API 28 起已经废弃。历史值 1、2、3 在现代 Android 中不再分别代表“仅设备”“省电”“高精度”，通常只具有定位开启的含义。

建议拆分为：

- 定位服务总开关；
- 应用精确/模糊定位权限；
- GNSS、网络定位等 provider 可用性查询；
- 后台定位策略。

官方依据：[Settings.Secure.LOCATION_MODE](https://developer.android.com/reference/android/provider/Settings.Secure)。

### 5.3 ASR-0318：NFC 传输数据

如果该需求指 Android Beam，则属于过时能力。Android 10 起 Android Beam 已被废弃且不再活跃开发。Android 13 下必须明确需求究竟是 NFC 标签读写、NDEF、HCE、支付、安全元件还是厂商自定义点对点传输。

官方依据：[Android 10 behavior changes](https://developer.android.com/about/versions/10/behavior-changes-all)。

### 5.4 ASR-0366：设置锁屏密码

不能定义成普通 MDM 命令随时直接修改密码。Android 13 的受控方案是预先配置并激活密码重置 token，再使用 `resetPasswordWithToken()`，同时满足密码质量和安全启动约束。

建议将 token 初始化、激活状态查询、密码策略校验、重置操作和失败恢复分别定义。

官方依据：[DevicePolicyManager.resetPasswordWithToken](https://developer.android.com/reference/android/app/admin/DevicePolicyManager)。

### 5.5 ASR-0444：禁用在线 FOTA

当前备注把 `SystemUpdatePolicy.TYPE_POSTPONE` 解释成“禁用在线 FOTA”。标准 Android 的 postponed 策略只允许对某个更新延期最多 30 天，重新设置策略不能无限延长期限。

因此当前实现只能满足“延期安装”，不能满足“无限期禁用在线 FOTA”。如确实需要完全禁用，必须由定制 ROM 的升级服务实施，同时保留安全更新和维修恢复机制。

官方依据：[Manage system updates](https://developer.android.com/work/dpc/system-updates)。

### 5.6 ASR-0258：获取 SIM 卡电话号码

SIM 或运营商订阅中可能没有写入本机号码，即使具备系统权限，相关接口仍可能返回空值。该需求只能承诺“查询并如实返回可用状态”，不能承诺一定取得号码。

官方依据：[TelephonyManager.getLine1Number](https://developer.android.com/reference/android/telephony/TelephonyManager.html)。

### 5.7 ASR-0261：获取 MEID

MEID 只适用于相关 CDMA 制式和硬件。对于不支持的产品型号，应返回 `supported=false`，不得作为全部 SKU 的必选成功用例。

### 5.8 ASR-0211、ASR-0148、ASR-0170：MAC 地址语义

“获取 MAC”和“MAC 黑白名单”没有明确地址对象。至少需要区分：

- Wi-Fi 工厂 MAC；
- 当前联网使用的每 SSID 随机 MAC；
- SoftAP MAC；
- Wi-Fi Direct MAC；
- 蓝牙设备地址；
- 以太网 MAC；
- 热点客户端当前报告的 MAC。

Android 10 起 Wi-Fi client、SoftAP 和 Wi-Fi Direct 默认支持 MAC 随机化。基于客户端 MAC 的黑名单只能作为运营策略，不能作为可靠身份认证机制。

官方依据：[AOSP Wi-Fi MAC randomization](https://source.android.com/docs/core/connect/wifi-mac-randomization)。

### 5.9 ASR-0327：强制加密 SD 卡

外置 SD 卡加密能力取决于存储模式、文件系统、vold、硬件密钥和产品是否支持 adoptable storage。需求不能只归属 Launcher，也不能保证在所有 SD 卡和文件系统上成立。

建议先确定产品存储架构，再定义支持条件、格式化行为、密钥丢失处理和跨设备不可读规则。

| ASR-0036 | 未说明“应用锁”由谁提供、锁什么界面、如何认证 |
| ASR-0056 | “通知样式”可能指渠道重要性、横幅、锁屏、角标、声音或具体 UI |

这些需求重写时至少应补充：

- 被控制的系统组件；
- 策略状态与当前运行状态；
- 支持条件和 `supported` 返回；
- 包名、签名或用户范围；
- 策略冲突优先级；
- 重启和恢复出厂后的状态；
- 异常码和失败后的系统状态；
- 可在真机执行的验收步骤。

## 7. 与当前硬件和机器人产品定位不匹配的需求

### 7.1 NFC 能力

当前测试机已经确认没有 NFC 硬件、NFC HAL、NfcService 和 `android.hardware.nfc` feature。因此 ASR-0315～ASR-0318 不应继续作为当前 SKU 的必选成功需求。

建议：

- 当前 SKU 标记为“不适用”；
- 接口可以保留统一能力查询，但应返回 `supported=false`；
- 只有未来包含 NFC BOM 的 SKU 才执行开关、纠正器和真实射频验收。

### 7.2 通话、短信、SIM 和联系人能力

ASR-0233～ASR-0309 覆盖完整消费手机 telephony 能力，包括通话限制、自动录音、短信黑白名单、号码归属、SIM PIN、联系人和 APN。

如果机器人只使用移动数据而不承担电话和短信业务，建议只保留：

- SIM 和订阅状态查询；
- 移动数据开关和状态；
- 默认数据卡；
- APN 配置；
- 信号、MCC/MNC、漫游和网络类型；
- 必要的流量统计与故障诊断。

通话录音、短信次数、号码脱敏、联系人导入、自动重拨和呼叫转移等功能应降为可选模块，不应进入默认机器人版本。

### 7.3 消费手机功能

以下需求只有在存在明确机器人业务用例时才应保留：

- ASR-0086～ASR-0107：默认短信、拨号、Assistant、浏览器历史、YouTube、支付应用；
- ASR-0355～ASR-0357：指纹和面部解锁；
- ASR-0380～ASR-0382：相册分享、小米账户和 Google 账户；
- ASR-0417～ASR-0430：护眼、耳机、语音助手、家长控制、查找手机和红外。

这些能力技术上并非全部不合理，但没有业务用例时，ROM 维护、回归测试和安全攻击面的成本明显高于价值。

### 7.4 ASR-0436：输入法支持所有国家和地区语言

“所有国家和地区语言”没有封闭集合，也无法定义完整验收范围。语言、键盘布局、输入法词库、右到左排版、组合字符和语音输入是不同能力。

建议根据销售地区给出明确的 BCP 47 locale 列表、键盘布局、物理键盘要求和验收文本，不要使用“所有语言”的绝对表述。

### 7.5 ASR-0438：CTS、STS、VTS、GTS 全部通过

CTS、STS、VTS 和 GTS 的目的、获取渠道、版本、硬件夹具和授权条件不同。GTS 与 Google/GMS 合作范围有关，不能仅由 ROM 开发团队单方面承诺。

建议拆分为：

- Android 13 指定版本 CTS；
- 与 BSP/HAL 对应版本的 VTS/CTS-on-GSI；
- 指定安全补丁周期的 STS；
- 只有产品需要并取得 GMS 授权时才纳入 GTS；
- 明确 build 类型、测试包版本、零失败要求、允许豁免和复测规则。

官方依据：[Android platform testing](https://source.android.com/docs/core/tests)。

### 7.6 ASR-0439：上电自动启动

该目标对机器人合理，但实现归属不能只写 ROM。断电后上电启动通常依赖 PMIC、充电 IC、主板电路、bootloader 和 kernel 电源状态机。

建议改为硬件与系统联合需求，并覆盖：

- 电池存在和不存在两种场景；
- 低电压和电池深度放电；
- 反复抖动上电；
- 充电器功率不足；
- 异常断电后的文件系统和业务恢复。

### 7.7 ASR-0442：WebView 灰度发布和失败告警

查询 WebView Provider 可以由 MDM 完成，但 Beta 预验证、灰度发布、版本策略、升级监控和失败告警还依赖 OTA/应用发布后台、制品签名、设备分组和遥测服务。

因此该条目不应只归属 Launcher，应拆成设备端和服务端两组需求。

### 7.8 ASR-0459、ASR-0460：100% 亮度和永久常亮

机器人上位机可能确实需要常亮，但无条件使用 100% 亮度会增加发热、功耗、背光老化和烧屏风险。

建议改为条件策略：

- 外接稳定电源且温度正常时保持常亮；
- 按环境和面板能力设定量产默认亮度；
- 高温、低电量和充电异常时自动降亮度或熄屏；
- 增加静态画面防烧屏和像素偏移策略；
- 保留 MDM 临时唤醒和恢复默认显示策略。

## 8. 需求分级建议

### 8.1 机器人核心必选

建议集中在以下能力：

- 受控安装、卸载和版本回滚；
- kiosk、默认 Launcher 和核心应用保活；
- 有线网络、Wi-Fi、必要的移动数据和 VPN；
- USB/ADB 的开发、量产和维修模式隔离；
- 设备证书、调用方身份和策略审计；
- 日志、运行状态、崩溃和硬件健康上报；
- 签名 OTA、A/B 回滚和断电恢复；
- 屏幕、电源、音量和机器人外设的确定性策略；
- 工厂初始化、设备所有者和受控维修流程。

### 8.2 硬件条件适用

只有 BOM 实际包含对应硬件时启用和验收：

- NFC；
- SIM/蜂窝语音；
- 外置 SD；
- 红外；
- 有线耳机；
- 指纹和人脸；
- 特定摄像头、闪光灯和传感器。

### 8.3 消费手机可选

默认不进入机器人基础版本：

- 通话、短信、联系人；
- 账户体系和应用商店；
- 相册分享；
- 家长控制和查找手机；
- 支付、Assistant、游戏和厂商侧边栏；
- 通话次数、号码归属和自动重拨等运营商功能。

### 8.4 建议拒绝实现

- 绕过锁屏认证的通用解锁接口；
- 向任意应用动态授予任意系统权限；
- 静默监听所有第三方 VoIP 通话；
- 删除所有前台服务和系统安全提示；
- 永久关闭所有升级、恢复和维修通道；
- 向普通业务应用开放 Device Owner 设置和删除；
- 无条件访问任意第三方应用私有数据和浏览历史。

## 9. 后续整理建议

建议对原始需求执行以下整理流程：

1. 从有效表中移出历史和空白需求；
2. 合并重复需求，区分策略状态和运行状态；
3. 为每个硬件相关需求增加适用 SKU 和 `supported` 语义；
4. 为每个高权限接口规定调用方签名、包名白名单和审计要求；
5. 将 bootloader、recovery、ROM、MDM、业务应用和服务端责任分开；
6. 删除无法安全实现的后门式需求；
7. 将消费手机功能从机器人基础版本中拆出；
8. 为保留需求补充状态模型、参数、返回值、异常和真机验收步骤；
9. 建立安全、可靠性、可维护性和 CTS/VTS 影响评审；
10. 最终形成一份数量更少但可以稳定实现、升级和验收的机器人系统需求基线。
